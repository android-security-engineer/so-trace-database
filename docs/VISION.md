# SO Trace Database — 产品愿景

## 一句话定义

**SO Trace Database 是一个专为 Android 平台 SO（共享库）逆向分析场景设计的执行轨迹存储与查询数据库。**

## 问题背景

在 Android 逆向工程中，对 SO 文件进行动态分析时需要采集程序运行轨迹（trace），包括指令执行序列、函数调用链、内存读写、JNI 交互等。现有工具链存在以下核心痛点：

### 痛点 1：Trace 数据量巨大，存储效率低下

- 一条指令级 trace 每秒可产生数百万条记录，几分钟的 trace 轻松达到 GB 级别
- 现有工具（Frida、Pin、DynamoRIO）通常将 trace 输出为纯文本或简单二进制文件，缺乏压缩和去重
- 大量重复模式（循环、公共函数）被原样存储，造成存储浪费

### 痛点 2：缺乏结构化查询能力

- 逆向分析师常常需要回答："哪些函数访问了这块内存？""这个解密函数的调用链是什么？""从用户输入到这个敏感 API 经过了哪些路径？"
- 现有方案（文本日志、简单数据库）无法高效回答这些查询
- 分析师被迫编写临时脚本处理原始 trace，效率低下且不可复用

### 痛点 3：Trace 与二进制上下文割裂

- Trace 数据与反编译/反汇编结果、符号信息、内存布局等上下文分散存储
- 分析师需要手动在 IDA/Ghidra 与 trace 数据之间来回切换
- 缺乏统一的关联查询能力

### 痛点 4：多源 Trace 数据无法统一管理

- Android 逆向中可能同时使用 Frida（函数级）、DynamoRIO/Pin（指令级）、strace（系统调用级）等多种采集工具
- 不同工具输出的 trace 格式各异，无法统一存储和交叉分析
- JNI 调用跨越 Java/Native 边界，trace 数据天然分裂

## 产品愿景

**让 Android SO 逆向分析师像数据库工程师查询业务数据一样，高效地存储、查询和分析程序执行轨迹。**

### 核心价值主张

1. **高效存储**：针对 trace 数据的特征（时序性、高重复、结构化）提供专用压缩和存储方案，相比原始文本实现 10x+ 存储压缩比
2. **结构化查询**：提供领域特定的查询语言或 API，支持按地址、函数、调用链、数据流等维度高效检索 trace
3. **上下文关联**：将 trace 与 SO 二进制的反编译结果、符号表、内存布局等自动关联
4. **多源统一**：支持多种采集工具（Frida、Pin、DynamoRIO 等）的 trace 数据导入，提供统一的存储和查询接口
5. **JNI 感知**：原生理解 Android JNI 调用边界，支持 Java ↔ Native 跨边界 trace 查询

### 目标用户

- Android 安全研究员
- SO 文件逆向工程师
- 恶意软件分析师
- 漏洞研究人员
- CTF 选手

### 非目标（明确排除）

- 不做通用的程序分析框架（如 Triton、angr 的符号执行引擎）
- 不做 trace 数据的采集工具（复用现有 Frida/Pin/DynamoRIO 等）
- 不做 GUI 可视化前端（专注数据库层，可视化由上层工具对接）
- 不做 Windows/macOS/Linux 平台（专注 Android）

## 成功标准

| 指标 | 目标 |
|------|------|
| 存储压缩比 | 相比原始文本 trace ≥ 10x |
| 写入吞吐 | ≥ 100 万条 trace 记录/秒 |
| 点查询延迟 | 按地址/函数名查询 < 10ms |
| 范围查询延迟 | 按时间窗口/调用链查询 < 100ms |
| 支持的 trace 规模 | 单次 trace ≥ 10 亿条记录 |
| 多源支持 | 至少支持 Frida、DynamoRIO、strace 三种输入 |
